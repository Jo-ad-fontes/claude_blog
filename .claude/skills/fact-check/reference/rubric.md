# fact-check 판정 기준

## PASS

- claims 배열에 근거가 있고
- claim-verifier가 그 출처를 다시 확인했고
- 지금도 정확히 일치한다

예: "obra/superpowers는 약 28만 스타를 가진다" → 출처 다시 열어서 27.9만~28만
범위면 PASS.

## WARNING

다음 중 하나라도 해당하면 WARNING (FAIL은 아니지만 사람이 봐야 함):

- 숫자가 자연스럽게 변함 (스타 수 증가/감소, 최근 커밋 날짜 등)
- 클레임 문구가 출처와 미묘하게 다름 (의미는 같지만 표현이 다름)
- `source_kind` 분류가 애매함 (예: 공식 저장소의 Discussion 탭 — official_docs인지
  community인지 경계)
- 출처는 맞지만 더 최신 정보가 다른 곳에 있는 것으로 보임

예: 초안 작성 시점엔 "25,000 포크"였는데 지금 다시 보니 "25,400 포크" → WARNING,
FAIL 아님. 사람이 숫자만 갱신하면 됨.

## FAIL

다음 중 하나라도 해당하면 FAIL (전체 verdict를 FAIL로 끌어내림):

- claims 배열에 아예 없는 문장이 초안에 있음 (write-review의 규칙 위반)
- 출처에 접근할 수 없음 (404, 삭제됨, 로그인 필요)
- 출처를 다시 읽어봐도 그 클레임을 뒷받침하지 않음
- 클레임이 명백히 틀렸음 (예: 다른 프로젝트의 사실과 혼동)
- 인용이 15단어를 넘거나, 같은 출처에서 두 번째 인용을 씀 (저작권 규칙 위반)

예: 초안에 "이 플러그인은 무료다"라고 썼는데 출처를 다시 보니 유료 티어가
생겼다 → FAIL. 단순 숫자 변화가 아니라 결론 자체가 바뀌는 경우다.

## 애매한 경우 판단하는 법

**"결론이 바뀌는가, 숫자만 바뀌는가"**로 구분한다. 숫자가 바뀌어도 글의
결론(추천 여부, 특징 설명)이 그대로면 WARNING. 결론까지 흔들리면 FAIL.

**write-review가 잘못한 것 vs 세상이 바뀐 것**도 구분해서 `unsourced_statements`와
`results`에 각각 남긴다. 전자는 Skill 설계를 고쳐야 할 신호이고, 후자는 그냥
초안을 갱신하면 되는 신호다 — 원인이 다르면 조치도 다르다.
